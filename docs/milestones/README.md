## 이 문서들을 읽는 법

- 팀원 각자가 자기 폴더에서 아래 작업을 모두 구현합니다. **[공용]** 표시가 붙은 작업만 루트 공용 영역에서 팀이 함께 진행합니다.
- "스터디 → 각자 구현 → 회고" 사이클의 단위는 M0, M1-1~M1-3, M2, M3-1~M3-3, M4입니다. M1과 M3의 하위 단계는 각 파일 안의 절로 나눴습니다. M7, M8, M12는 착수 전에 하위 단계로 나눌지 다시 판단합니다.
- 단계마다 적힌 "미리 공부할 기술"이 그 단계 직전 스터디의 주제 후보입니다.
- 작업 단위는 [하네스의 작업 단위 설계](../harness/personal_convention/handoff_convention.md) 기준에 따라 "독립적으로 확인할 수 있는 동작 하나"로 나눴습니다. 작업마다 아래 항목을 밝혔습니다.
  - **목표 동작:** "무엇을 하면 무엇이 된다"는 한 문장입니다.
  - **관련 기능:** feature-spec의 기능 ID입니다. 기반 작업처럼 해당 기능이 없으면 "없음"으로 표시했습니다.
  - **확인 방법:** 그 동작을 확인하는 테스트나 명령입니다.
  - **결정 의존:** 착수 전에 정해야 하는 정책이나 팀 결정입니다. 결정이 나기 전에는 결정이 필요 없는 작업부터 진행할 수 있습니다.
- 작업의 순서는 나열한 순서를 권장합니다. 앞 작업이 만든 코드를 뒤 작업이 사용하도록 배치했습니다.
- 이슈와 이슈별 핸드오프의 작업 단위 목록을 만들 때 이 작업 단위를 출발점으로 사용할 수 있습니다.

## Plus (개요)

착수 전에 Core 구현을 바탕으로 구체화합니다.

### M5 대기열과 실시간 화면

- Redis ZSet 대기열과 입장 토큰을 구현합니다(QUE-01, QUE-03).
- SSE로 순번을 전달하고, 순번 화면을 만듭니다(QUE-02, QUE-04). 화면의 소유 방식은 계획서 8절의 남은 항목입니다.
- 시나리오 4로 다섯 번째 방식(대기열+Lua+Outbox+Kafka)을 비교합니다.
- **완료 조건:** 대기열 유무에 따른 DB 쿼리 수와 p99를 비교했습니다.

### M6 운영 품질

- Idempotency-Key와 reconciliation을 구현합니다(OPS-01, OPS-03).
- 요청 횟수 제한을 구현합니다(OPS-02).
- Toxiproxy로 장애 주입을 자동화하고, 알람 규칙과 런북을 작성합니다(OPS-04, OPS-05).
- **완료 조건:** 장애 주입 시 알람이 실제로 발생하고 불변식 검사가 통과합니다.

## Expand (개요)

Core와 Plus의 완료 조건을 충족한 뒤에 착수하며, 원하는 순서로 진행할 수 있습니다.

### M7 알림 서비스 분리

- `notification-service`를 분리하고, 이벤트 계약 테스트와 OpenTelemetry 트레이싱을 도입합니다.
- 오픈 시각 알림과 취소표 알림 구독을 구현합니다(NTF-01~NTF-04).
- **완료 조건:** 알림 서비스를 중지해도 예약이 정상이고, 복구 후 유실과 중복이 없습니다.

### M8 검색·집계·랭킹

- Kafka 이벤트를 소비하는 Elasticsearch 인덱서와 검색·통계 API를 만듭니다(SRCH-01, SRCH-02, SRCH-05).
- 조회수 write-behind와 ZSet 인기 랭킹을 구현합니다(SRCH-03, SRCH-04).
- **완료 조건:** DB 장애와 무관하게 검색이 동작하고, 재색인과 랭킹 복원이 가능합니다.

### M9 선착순 쿠폰

- 총량·1인 1매·기간 제한을 Redis 재고와 DB 원장으로 처리합니다(CPN-01, CPN-02).
- 결제 시 쿠폰 적용과 취소 시 반환을 연동합니다(CPN-03, CPN-04).
- **완료 조건:** 총량 초과 발급과 중복 발급이 0건입니다.

### M10 정산 배치

- `settlement-batch`를 독립 서비스로 분리하고 Spring Batch로 정산합니다(STL-01~STL-03).
- **완료 조건:** 재실행과 강제 종료 후 재시작에도 합계가 일치합니다.

### M11 부정 예매 방지와 감사 로그

- 구매 한도, 봇 의심 패턴 탐지, 상태 변경 이력을 구현합니다.
- **완료 조건:** 한도 초과 요청이 차단되고, 모든 상태 변경 이력이 조회됩니다.

### M12 클라우드 인프라

- Terraform으로 VM과 k3s를 구성하고, Helm으로 Jenkins를 설치해 CD 파이프라인을 만듭니다.
- 인프라를 각자 구성할지 공용으로 운영할지는 계획서 8절의 남은 항목입니다.
- **완료 조건:** Jenkins로 배포와 롤백을 1회 수행하고, 클라우드 환경에서 1회 재측정했습니다.
