# M1 핵심 도메인

> [마일스톤 목록](README.md) · 이전: [M0 기반 준비](m0.md) · 다음: [M2 동시성 1차](m2.md)

- **목표:** 주최자가 등록한 행사를 구매자가 예약할 수 있는 기본 흐름을 만듭니다. 동시성 제어는 M2에서 다룹니다.
- **하위 단계:** M1-1 회원·인증·권한 → M1-2 주최자 백오피스 → M1-3 좌석 조회와 예약. 하위 단계마다 "스터디 → 각자 구현 → 회고" 사이클을 진행합니다.
- **선행 조건:** M0 완료, 공용 API 명세 초안과 예약 상태 전이도

## M1-1 회원·인증·권한

- **미리 공부할 기술:** Spring Security 필터 체인, OAuth2 Client(소셜 로그인), JWT와 Refresh Token 회전, Redis 기초, Flyway
- **관련 기능:** AUTH-01~07
- **결정 의존(단계 전체):** 소셜 로그인 제공자(M1 착수 전), 노션 정책서의 "토큰 수명"

### 1. 회원 테이블과 Flyway

- **목표 동작:** 앱을 띄우면 Flyway가 회원 테이블을 만들고, 회원을 저장하고 조회할 수 있습니다.
- **관련 기능:** 없음(AUTH 기반)
- **확인 방법:** Testcontainers(PostgreSQL)로 마이그레이션 적용과 회원 저장·조회 테스트
- **결정 의존:** 없음

### 2. 소셜 로그인과 토큰 발급

- **목표 동작:** 소셜 로그인에 성공하면 처음 온 사용자는 구매자(BUYER)로 가입되고, 자체 Access Token과 Refresh Token을 받습니다.
- **관련 기능:** AUTH-01
- **확인 방법:** 신규 가입과 기존 회원 로그인을 각각 확인하는 통합 테스트. 테스트에서 실제 제공자에 접속하지 않도록 제공자의 응답(사용자 정보)을 흉내 냅니다. Spring Security 테스트의 OAuth2 로그인 지원 기능이나 가짜 HTTP 서버를 활용할 수 있으며, 방법은 각자 정합니다.
- **결정 의존:** 소셜 로그인 제공자, 토큰 수명

### 3. 인증 필터와 내 정보 조회

- **목표 동작:** 유효한 Access Token으로 내 정보를 조회하면 이름, 이메일, 권한이 돌아오고, 토큰이 없거나 만료되었으면 401이 돌아옵니다.
- **관련 기능:** AUTH-04
- **확인 방법:** 정상 토큰, 토큰 없음, 만료 토큰의 세 경우를 확인하는 API 테스트
- **결정 의존:** 없음

### 4. 토큰 재발급과 회전

- **목표 동작:** Refresh Token으로 새 토큰 쌍을 받으면 이전 Refresh Token은 무효가 되고, 이미 사용한 Refresh Token이 다시 오면 그 사용자의 모든 세션이 끊깁니다.
- **왜 하는가:** Refresh Token은 수명이 길어서 탈취되면 오래 악용될 수 있습니다. 사용할 때마다 새 토큰으로 바꾸면(회전), 탈취된 옛 토큰이 다시 들어오는 순간 탈취를 알아채고 세션을 끊을 수 있습니다.
- **관련 기능:** AUTH-02
- **확인 방법:** Testcontainers(PostgreSQL, Redis)로 정상 회전과 재사용 탐지를 각각 확인합니다.
- **결정 의존:** 없음. 토큰 저장 위치는 각자 정하고 ADR에 기록합니다.

### 5. 로그아웃과 블랙리스트

- **목표 동작:** 로그아웃하면 Refresh Token이 지워지고, 남은 Access Token은 만료될 때까지 Redis 블랙리스트에 등록되어 거절됩니다.
- **관련 기능:** AUTH-03
- **확인 방법:** 로그아웃 후 같은 Access Token으로 요청하면 401이 돌아오는지 확인하는 통합 테스트
- **결정 의존:** 없음

### 6. 경로별 권한 검사

- **목표 동작:** 경로마다 필요한 권한(BUYER, ORGANIZER, ADMIN)이 없는 요청은 403으로 거절됩니다.
- **관련 기능:** AUTH-07. "주최자는 자기 행사만 수정한다"는 검사는 행사가 생기는 M1-2 작업 1에서 함께 구현합니다.
- **확인 방법:** 권한별로 허용, 거절되는 경로를 확인하는 API 테스트
- **결정 의존:** 없음

### 7. 권한 부여와 회수

- **목표 동작:** 관리자가 회원에게 주최자 권한을 주거나 회수하면, 그 회원의 다음 요청부터 바뀐 권한이 적용됩니다.
- **관련 기능:** AUTH-06
- **확인 방법:** 권한 부여 전후로 주최자 전용 경로의 응답이 바뀌는지 확인하는 API 테스트
- **결정 의존:** 노션 정책서의 "주최자 승인"

### 8. 회원 탈퇴

- **목표 동작:** 구매자나 주최자가 탈퇴하면 탈퇴가 처리됩니다. 탈퇴한 계정의 상태와 이후 로그인 처리는 노션 정책서의 "탈퇴 조건"을 따릅니다.
- **관련 기능:** AUTH-05. 진행 중인 예약이 있으면 탈퇴를 막는 검사는 M1-3 작업 5에서, 탈퇴 이벤트 발행은 M3-2에서 연결합니다.
- **확인 방법:** 탈퇴 후 계정이 정책서에 정한 상태가 되는지 확인하는 통합 테스트
- **결정 의존:** 노션 정책서의 "탈퇴 조건"

### M1-1 완료 조건

소셜 로그인부터 토큰 회전, 로그아웃까지 통합 테스트가 통과하고, 역할별 접근 제어가 공용 API 명세와 일치합니다.

- **ADR 후보:** 토큰 저장 위치와 블랙리스트 방식

## M1-2 주최자 백오피스

- **미리 공부할 기술:** AWS S3와 IAM 최소 권한, LocalStack, JPA 연관관계, QueryDSL, ShedLock
- **관련 기능:** ORG-01~06, EVT-01~02

### 공용 작업: [공용] S3 운영 규칙 결정

- **목표 동작:** 키 보관 방식, IAM 정책, 팀원별 버킷 여부, AWS Budgets, 테스트용 대체물(LocalStack 등) 사용 여부가 정해져 있습니다.
- **관련 기능:** ORG-05
- **확인 방법:** 결정 내용을 컨벤션과 결정 기록에 남깁니다.
- **결정 의존:** 팀 결정(M1 착수 전)

### 1. 행사 등록과 수정

- **목표 동작:** 주최자가 행사(제목, 설명, 장소, 카테고리)를 등록하고 수정할 수 있으며, 다른 주최자의 행사를 수정하면 403이 돌아옵니다.
- **관련 기능:** ORG-01, AUTH-07(자기 행사 검사). 행사 변경 이벤트 발행은 M3-2에서 연결합니다.
- **확인 방법:** 등록, 수정, 다른 주최자의 수정 거절을 확인하는 API 테스트
- **결정 의존:** 노션 정책서의 "행사 수정 제한"

### 2. 회차 등록

- **목표 동작:** 주최자가 행사에 공연 일시, 예매 오픈 시각, 마감 시각을 가진 회차를 등록하면 회차가 `SCHEDULED` 상태로 만들어집니다.
- **관련 기능:** ORG-03
- **확인 방법:** 정상 등록과, 노션 정책서 "예매 오픈"이 정한 조건을 어긴 요청의 거절을 확인하는 API 테스트
- **결정 의존:** 노션 정책서의 "예매 오픈"

### 3. 좌석 배치·등급·가격 등록

- **목표 동작:** 주최자가 회차의 좌석(구역, 열, 번호)과 등급, 등급별 가격을 한 번에 등록할 수 있고, 회차가 `SCHEDULED`가 아니면 거절됩니다.
- **관련 기능:** ORG-04
- **확인 방법:** 일괄 등록과 오픈 후 변경 거절을 확인하는 API 테스트
- **결정 의존:** 노션 정책서의 "행사 수정 제한"

### 4. 내 행사 목록

- **목표 동작:** 주최자가 자기가 등록한 행사와 회차별 판매 현황을 조회합니다. 판매 수는 M1-3에서 예약이 생긴 뒤부터 실제 값이 됩니다.
- **관련 기능:** ORG-02
- **확인 방법:** 다른 주최자의 행사가 섞이지 않는지 확인하는 API 테스트
- **결정 의존:** 없음

### 5. 행사 목록 동적 검색

- **목표 동작:** 누구나 카테고리, 기간, 판매 상태를 조합해 행사 목록을 조회할 수 있습니다.
- **관련 기능:** EVT-01
- **확인 방법:** 조건 조합별 조회 결과를 확인하는 테스트. QueryDSL 쿼리의 EXPLAIN 결과를 자기 폴더의 `docs/`에 기록합니다.
- **결정 의존:** 없음

### 6. 행사 상세

- **목표 동작:** 누구나 행사 정보와 회차 목록을 조회할 수 있습니다.
- **관련 기능:** EVT-02
- **확인 방법:** API 테스트
- **결정 의존:** 없음

### 7. 행사 이미지 업로드

- **목표 동작:** 주최자가 요청하면 서버가 S3 Presigned URL을 발급하고, 그 URL로 올린 이미지가 행사에 연결됩니다.
- **왜 하는가:** 이미지를 서버가 직접 받아 S3로 넘기면 파일이 서버를 거치는 만큼 대역폭과 메모리를 소모합니다. Presigned URL은 정해진 시간 동안만 유효한 업로드 권한이 담긴 주소라서, 클라이언트가 서버를 거치지 않고 S3에 바로 올릴 수 있습니다.
- **관련 기능:** ORG-05
- **확인 방법:** 실제 AWS 키 없이 도는 테스트(공용 작업에서 정한 대체물 사용)로 URL 발급과 업로드를 확인합니다.
- **결정 의존:** 공용 작업(S3 운영 규칙), 노션 정책서의 "이미지 제한"

### 8. 예매 오픈 자동 전환

- **목표 동작:** 오픈 시각이 되면 회차가 `SCHEDULED`에서 `OPEN`으로, 마감 시각이 되면 `CLOSED`로 바뀌며, 서버가 여러 대여도 한 번만 실행됩니다.
- **왜 하는가:** 서버를 여러 대 띄우면 서버마다 있는 스케줄러가 같은 시각에 함께 돌아, 같은 전환을 여러 번 실행합니다. ShedLock은 공용 저장소(DB 등)에 잠금 기록을 남겨, 그 시각에는 한 서버만 작업을 실행하게 합니다.
- **관련 기능:** ORG-06
- **확인 방법:** 시각에 따른 상태 전환을 확인하는 테스트(테스트에서 현재 시각을 바꾸는 방법은 각자 정합니다), 스케줄러를 두 개 띄워도 한 번만 실행되는지 확인하는 테스트
- **결정 의존:** 노션 정책서의 "예매 오픈"

### M1-2 완료 조건

주최자가 행사·회차·좌석을 등록하고 이미지를 올릴 수 있으며, 오픈 시각에 예매가 열립니다.

## M1-3 좌석 조회와 예약

- **미리 공부할 기술:** 대량 데이터 생성. 트랜잭션 경계와 `@Transactional` 속성은 사전 5회차(Spring), 인덱스 설계는 사전 6회차(DB) 내용을 복습합니다.
- **관련 기능:** EVT-03, RSV-01~03, AUTH-05(예약 검사), BENCH-01

### 1. 회차 좌석 조회

- **목표 동작:** 구매자가 회차의 좌석 배치와 좌석별 상태, 등급, 가격을 조회할 수 있습니다.
- **관련 기능:** EVT-03
- **확인 방법:** API 테스트
- **결정 의존:** 없음

### 2. 좌석 선점(예약 생성)

- **목표 동작:** 구매자가 `OPEN` 회차의 좌석을 고르면 좌석은 `HELD`, 예약은 `PENDING`이 되고 결제 마감 시각(`expiresAt`)이 정해집니다. 이 단계에서는 동시성 제어 없이 기본 흐름만 만듭니다.
- **관련 기능:** RSV-01(동시성 제어는 M2)
- **확인 방법:** 정상 선점, 이미 `HELD`인 좌석의 거절, `OPEN`이 아닌 회차의 거절을 확인하는 Testcontainers 통합 테스트
- **결정 의존:** 노션 정책서의 "선점 유지 시간", "1회 최대 좌석 수", 공용 예약 상태 전이도

### 3. 예약 조회

- **목표 동작:** 구매자가 내 예약 목록과 예약 상세(좌석, 금액, 상태, 결제 마감 시각)를 조회할 수 있고, 다른 사람의 예약은 조회할 수 없습니다.
- **관련 기능:** RSV-02
- **확인 방법:** API 테스트
- **결정 의존:** 없음

### 4. 결제 전 예약 취소

- **목표 동작:** 구매자가 `PENDING` 예약을 취소하면 예약은 `CANCELED`, 좌석은 `AVAILABLE`이 됩니다.
- **관련 기능:** RSV-03. `CONFIRMED` 예약의 환불 후 취소는 M3-3에서 연결합니다.
- **확인 방법:** 취소 후 같은 좌석을 다시 선점할 수 있는지 확인하는 통합 테스트
- **결정 의존:** 노션 정책서의 "취소·환불"

### 5. 탈퇴 시 진행 중 예약 검사

- **목표 동작:** 진행 중인 예약이 있는 회원이 탈퇴하려 하면 거절됩니다.
- **관련 기능:** AUTH-05
- **확인 방법:** 예약이 있을 때와 없을 때의 탈퇴 결과를 확인하는 통합 테스트
- **결정 의존:** 노션 정책서의 "탈퇴 조건"("진행 중"에 포함되는 예약 상태)

### 6. 측정용 데이터 생성 스크립트

- **목표 동작:** 스크립트를 실행하면 측정용 행사, 회차, 좌석, 회원이 만들어지며, "핫 좌석"과 "분산 좌석" 두 가지 분포를 고를 수 있습니다.
- **관련 기능:** BENCH-01
- **확인 방법:** 두 분포로 각각 실행한 뒤 생성된 데이터의 개수와 분포를 확인합니다.
- **결정 의존:** 없음

### M1-3 완료 조건

주최자가 등록한 행사를 구매자가 예약할 수 있고, 동작이 공용 API 명세와 일치하며, Testcontainers 통합 테스트가 통과합니다. 여기까지가 M1의 완료 조건입니다.
