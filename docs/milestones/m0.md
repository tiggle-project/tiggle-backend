# M0 기반 준비

> [마일스톤 목록](README.md) · 다음: [M1 핵심 도메인](m1.md)

- **목표:** 팀원 모두가 자기 폴더에서 앱과 의존 인프라를 띄우고 CI로 검증할 수 있는 상태를 만듭니다. 이후 단계가 함께 사용할 공용 명세의 초안도 작성합니다.
- **미리 공부할 기술:** Gradle 멀티모듈과 버전 카탈로그, Docker Compose profile, GitHub Actions(사전 7회차 개발 도구), 모듈형 모놀리스(사전 4회차 아키텍처 기초), ArchUnit(사전 8회차 테스트)
- **관련 기능:** 없음(기반 작업)
- **선행 조건:** 사전 스터디 9회 완료(노션 스터디 페이지 7절)

## 공용 작업

### 1. [공용] 원격 저장소와 공용 영역 배치

- **목표 동작:** 원격 저장소를 내려받으면 공용 영역(`docs/`, `specs/`, `loadtest/`, `.github/`)과 팀원별 폴더가 모두 들어 있습니다.
- **관련 기능:** 없음
- **확인 방법:** 팀원 모두가 저장소를 내려받아 폴더 구성을 확인합니다.
- **결정 의존:** 저장소 이름과 공개 여부, 팀원 GitHub 아이디

### 2. [공용] PR 템플릿, CODEOWNERS, 브랜치 보호

- **목표 동작:** PR을 열면 템플릿이 채워지고, 공용 영역을 바꾸는 PR에는 지정된 리뷰어가 자동으로 요청되며, 승인 없이는 `main`에 머지되지 않습니다.
- **관련 기능:** 없음
- **확인 방법:** 시험용 PR로 템플릿, 리뷰어 자동 지정, 머지 차단을 확인합니다.
- **결정 의존:** 협업 규칙(리뷰 승인 기준, 공용 영역의 확인 범위, 브랜치 전략)

### 3. [공용] API 명세 초안

- **목표 동작:** `specs/`의 OpenAPI 문서에 M1 범위(회원, 행사·회차, 좌석, 예약)의 엔드포인트와 요청·응답 형식이 정의되어 있습니다.
- **관련 기능:** AUTH-01~07, ORG-01~06, EVT-01~03, RSV-01~03
- **확인 방법:** OpenAPI 문법 검사 도구로 문서가 유효한지 확인하고, 팀 전원이 엔드포인트 목록을 검토합니다.
- **결정 의존:** 없음

### 4. [공용] 이벤트 봉투와 스키마 초안

- **목표 동작:** 모든 이벤트가 공통 봉투(이벤트 ID, 타입, 버전, 발생 시각)를 갖고, 예약·결제 이벤트의 본문 형식과 버전 정책이 `specs/`에 정의되어 있습니다.
- **관련 기능:** MSG-01, MSG-02(M3-2에서 사용)
- **확인 방법:** 팀 전원이 스키마를 검토합니다.
- **결정 의존:** 없음

### 5. [공용] 예약 상태 전이도

- **목표 동작:** 좌석, 예약, 결제, 회차의 상태와 허용되는 전이가 `specs/`의 상태 전이도에 확정되어 있습니다.
- **관련 기능:** RSV-01~06, PAY-01~05, ORG-06
- **확인 방법:** feature-spec "상태 흐름"의 초안과 대조해 팀 전원이 확인합니다. 확정되면 feature-spec의 "초안" 표시를 지웁니다.
- **결정 의존:** 없음

### 6. [공용] PostgreSQL 메이저 버전 결정

- **목표 동작:** 모든 팀원의 Compose와 Testcontainers가 같은 PostgreSQL 메이저 버전을 사용합니다.
- **관련 기능:** 없음
- **확인 방법:** 결정 내용을 컨벤션과 결정 기록에 남기고, 각자의 설정이 그 버전을 가리키는지 확인합니다.
- **결정 의존:** 팀 결정

## 개인 작업

### 1. Gradle 멀티모듈 골격

- **목표 동작:** 자기 폴더에서 `./gradlew build`를 실행하면 `ticketing-core` 모듈이 빌드되고, 라이브러리 버전은 `libs.versions.toml` 한 곳에서 관리됩니다(Spring Boot 3.5.x, Java 21).
- **왜 하는가:** Tiggle은 나중에 `mock-pg`(M3), `notification-service`(M7), `settlement-batch`(M10)처럼 따로 실행되는 서버가 늘어납니다. 처음부터 모듈을 추가할 수 있는 틀과 버전을 한 곳에서 관리하는 구조를 만들어 두면, 서버를 늘릴 때 모듈마다 라이브러리 버전이 달라지는 문제를 막을 수 있습니다.
- **진행 순서:**
  1. 자기 폴더에 Gradle 래퍼(`gradlew`)와 `settings.gradle.kts`를 만들고, `ticketing-core`를 하위 모듈로 등록합니다.
  2. `gradle/libs.versions.toml`에 Spring Boot와 주요 라이브러리 버전을 모읍니다.
  3. `ticketing-core/build.gradle.kts`가 버전을 직접 적지 않고 카탈로그를 참조하게 만듭니다.
  4. 빈 Spring Boot 애플리케이션 클래스와 테스트 하나를 두고 `./gradlew build`가 통과하는지 확인합니다.
- **범위:** M0에서는 `ticketing-core` 하나만 있으면 충분합니다. 다른 모듈은 필요한 단계에서 추가합니다.
- **관련 기능:** 없음
- **확인 방법:** `./gradlew build`
- **결정 의존:** 없음

### 2. 도메인 패키지와 경계 규칙

- **목표 동작:** `ticketing-core` 안에 도메인 패키지가 나뉘어 있고, 자기가 정한 도메인 간 참조 규칙을 어기면 ArchUnit 테스트가 실패합니다.
- **왜 하는가:** `ticketing-core`는 서버 하나 안에 여러 도메인을 패키지로 나눈 모듈형 모놀리스입니다. 도메인끼리 엔티티나 리포지토리를 마음대로 가져다 쓰면, 한 도메인을 고칠 때 다른 도메인이 함께 깨지고 M7처럼 일부를 별도 서버로 떼어 내기도 어려워집니다. 경계 규칙을 테스트로 만들어 두면 사람이 매번 리뷰로 잡지 않아도 CI가 막아 줍니다.
- **팀 공통으로 맞추는 것:** 도메인 구분뿐입니다. 개인 폴더 README의 "권장 구성"(`auth`, `organizer`, `reservation`, `payment`, `coupon`, `audit`)을 따릅니다. 회고에서 같은 도메인끼리 비교하기 위해서입니다.
- **각자 정하는 것:** 도메인 안의 패키지 이름과 파일 배치, 그리고 도메인끼리 무엇까지 참조를 허용할지(경계 규칙)입니다. 규칙과 그렇게 정한 이유는 PR 설명이나 ADR에 기록해 주세요. 서로 다른 선택은 회고의 비교 주제가 됩니다.
- **경계 규칙의 예시(참고용):**
  - **공개 창구 방식:** 도메인마다 다른 도메인에 공개할 클래스만 모은 패키지를 하나 두고, 다른 도메인은 그 패키지만 참조합니다. 예를 들어 탈퇴할 때 `auth`가 `reservation`에 "진행 중인 예약이 있는가"를 물을 때, `reservation`의 엔티티나 리포지토리 대신 공개된 조회 인터페이스만 호출합니다. 이 패키지는 HTTP 요청을 받는 컨트롤러와는 다릅니다.
  - **전면 금지 방식:** 도메인끼리는 어떤 클래스도 참조하지 않고, 공용 패키지와 이벤트로만 소통합니다. 가장 엄격하지만, 이벤트를 도입하는 M3 전에는 도메인 간 협력이 필요한 작업(예: M1-3 작업 5)을 구현하기 어렵습니다.
  - **최상위 패키지 공개 방식:** 도메인 최상위 패키지에 있는 클래스는 공개로, 하위 패키지는 내부로 봅니다. Spring Modulith가 이 방식을 기본으로 사용합니다.
- **진행 순서:**
  1. `ticketing-core`에 도메인 패키지를 만들고, 각 도메인에 빈 클래스를 하나씩 둡니다.
  2. 경계 규칙을 정하고, 규칙을 말 한 문장으로 적어 봅니다(예: "다른 도메인을 참조한다면 공개 패키지만 참조한다").
  3. 테스트 의존성에 ArchUnit을 추가하고, 그 문장을 ArchUnit 규칙 테스트로 옮깁니다.
  4. 규칙을 어기는 참조를 일부러 추가해 테스트가 실패하는지 보고, 지워서 다시 통과하는지 확인합니다.
- **관련 기능:** 없음
- **확인 방법:** 진행 순서 4
- **결정 의존:** 없음(경계 규칙은 각자 정합니다)

### 3. springdoc-openapi 연결

- **관련 기능:** 없음
- **확인 방법:** `/v3/api-docs`가 200을 돌려주는지 확인하는 테스트, Swagger UI 접속
- **결정 의존:** 없음

### 4. Docker Compose 구성

- **목표 동작:** `docker compose --profile <이름> up`으로 PostgreSQL, Redis, Kafka를 필요한 것만 띄우고, 앱이 그 인프라에 연결됩니다.
- **관련 기능:** 없음
- **확인 방법:** profile별로 띄운 뒤 앱의 헬스 체크(`/actuator/health`)가 UP인지 확인합니다.
- **결정 의존:** 공용 작업 6(PostgreSQL 버전)

### 5. GitHub Actions 워크플로

- **목표 동작:** 자기 폴더를 바꾼 PR에서만 빌드와 테스트가 자동으로 실행됩니다.
- **관련 기능:** 없음
- **확인 방법:** 자기 폴더를 바꾼 PR에서는 워크플로가 실행되어 통과하고, 다른 폴더만 바꾼 PR에서는 실행되지 않는지 확인합니다. 워크플로는 루트 `.github/workflows/<폴더 이름>.yml`에 `paths` 필터와 함께 배치합니다.
- **결정 의존:** 공용 작업 1(원격 저장소)

### 6. 기술 입문 스파이크

- **목표 동작:** 처음 접하는 기술 하나로 반나절 분량의 예제를 만들어 스터디에서 시연합니다.
- **관련 기능:** 없음

- **결정 의존:** 없음

## 완료 조건

팀원 모두의 폴더에서 `docker compose up`으로 앱과 의존 인프라가 뜨고, 각자의 CI가 통과합니다.
