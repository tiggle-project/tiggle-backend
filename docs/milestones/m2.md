# M2 동시성 1차

> [마일스톤 목록](README.md) · 이전: [M1 핵심 도메인](m1.md) · 다음: [M3 동시성 2차와 결제](m3.md)

- **목표:** 같은 좌석에 동시 요청이 몰려도 초과 판매가 생기지 않도록, 비관적 락, 낙관적 락, Redisson 분산 락의 세 방식을 구현하고 설정으로 교체할 수 있게 만듭니다.
- **미리 공부할 기술:** 비관적 락(`SELECT ... FOR UPDATE`), 낙관적 락(`@Version`)과 재시도, Redisson 분산 락. 동시성 테스트(`ExecutorService`, `CountDownLatch`)와 PostgreSQL 격리 수준은 사전 스터디 8회차(테스트)와 6회차(DB) 내용을 복습합니다.
- **관련 기능:** RSV-01(동시성 제어), RSV-06, BENCH-03
- **선행 조건:** M1 완료

## 공용 작업

### 1. [공용] 불변식 검사기 첫 버전

- **목표 동작:** 검사기를 실행하면 "확정 예약 수가 좌석 수를 넘지 않는다"를 DB에서 검사하고, 어긋나면 실패를 보고합니다.
- **관련 기능:** BENCH-03
- **확인 방법:** 일부러 초과 판매된 데이터를 만들었을 때 검사기가 실패하는지 확인합니다.
- **결정 의존:** 없음

### 2. [공용] 동시성 시나리오 1과 실험 조건

- **목표 동작:** 팀원 모두가 같은 조건으로 테스트하고 측정할 수 있도록 아래 값이 정해져 있습니다.
  - "한 좌석에 동시 요청 집중" 시나리오의 동시 요청 수, 좌석 수, 반복 횟수
  - 실험에 적용할 격리 수준
  - 동시성 전략을 고르는 설정 키(`tiggle.reservation.lock-strategy`, 초안)와 전략별 값. M4의 공용 측정 자동화가 모든 팀원의 구현에서 이 키로 전략을 바꿔 가며 측정합니다.
- **관련 기능:** RSV-06
- **확인 방법:** 조건을 `loadtest/`에 기록하고, 확정된 설정 키를 feature-spec RSV-06에 반영합니다.
- **결정 의존:** 팀 결정

## 개인 작업

### 1. 좌석 선점 전략 분리

- **목표 동작:** 공용 설정 키 하나로 좌석 선점 방식을 고를 수 있게 구조를 바꿉니다. 교체 구조(인터페이스와 구현 분리 등)는 각자 정합니다. 지금은 "제어 없음" 구현 하나뿐이며 동작은 M1-3과 같습니다.
- **왜 하는가:** 작업 4~6에서 방식을 하나씩 추가할 때 예약 서비스 코드를 고치지 않아도 되고, M4에서 같은 앱을 설정만 바꿔 방식별로 측정할 수 있습니다. 사전 4회차의 DIP와 OCP를 적용하는 자리입니다.
- **관련 기능:** RSV-06
- **확인 방법:** 동작을 바꾸지 않는 리팩터링이므로, M1-3의 예약 테스트가 그대로 통과하는지 확인합니다.
- **결정 의존:** 공용 작업 2(설정 키)

### 2. 동시성 테스트와 초과 판매 재현

- **목표 동작:** 공용 시나리오 1의 조건으로 동시 요청을 보내는 테스트가 있고, "제어 없음" 구현에서 초과 판매가 실제로 생기는 것을 이 테스트로 확인합니다.
- **관련 기능:** RSV-01
- **확인 방법:** Testcontainers 동시성 테스트와 공용 불변식 검사기. "제어 없음"에서는 초과 판매가 생기는 것을 기대하는 테스트로 문제를 재현하고, 작업 4~6에서는 같은 테스트로 0건을 기대합니다. 커밋은 항상 테스트가 통과하는 상태로 남깁니다. 테스트 메서드에 `@Transactional`을 붙이지 않고 데이터를 직접 정리합니다.
- **결정 의존:** 공용 작업 1, 2

### 3. 격리 수준 적용

- **목표 동작:** 공용 작업 2에서 정한 격리 수준이 설정에 반영되어 있습니다.
- **관련 기능:** 없음
- **확인 방법:** 실행 중인 커넥션의 격리 수준을 조회하는 테스트
- **결정 의존:** 공용 작업 2

### 4. 비관적 락 구현

- **목표 동작:** 설정을 비관적 락으로 바꾸면 시나리오 1에서 초과 판매가 0건이고 불변식 검사기가 통과합니다.
- **관련 기능:** RSV-01, RSV-06
- **확인 방법:** 작업 2의 동시성 테스트
- **결정 의존:** 없음

### 5. 낙관적 락과 재시도 구현

- **목표 동작:** 설정을 낙관적 락으로 바꾸면 충돌한 요청은 정해진 횟수만큼 재시도한 뒤 실패로 끝나고, 시나리오 1에서 초과 판매가 0건입니다.
- **관련 기능:** RSV-01, RSV-06
- **확인 방법:** 작업 2의 동시성 테스트, 재시도 횟수를 넘긴 요청의 실패 응답 확인
- **결정 의존:** 재시도 횟수와 간격(자기 구현에서 정하고 PR에 이유를 기록)

### 6. Redisson 분산 락 구현

- **목표 동작:** 설정을 Redisson으로 바꾸면 좌석 단위 분산 락으로 요청이 직렬화되고, 시나리오 1에서 초과 판매가 0건입니다.
- **관련 기능:** RSV-01, RSV-06
- **확인 방법:** Testcontainers(PostgreSQL, Redis) 동시성 테스트. 락 획득 대기 시간을 넘긴 요청의 실패 응답도 확인합니다.
- **결정 의존:** 없음

## 완료 조건

세 방식 모두 시나리오 1에서 초과 판매가 0건이고, 불변식 검사기가 통과합니다.

- **ADR 후보:** 세 락 방식의 선택 기준. 격리 수준은 공용 작업 2에서 팀이 정하고 그 이유를 결정 기록에 남깁니다.
