# M3 동시성 2차와 결제

> [마일스톤 목록](README.md) · 이전: [M2 동시성 1차](m2.md) · 다음: [M4 성능 측정](m4.md)

- **목표:** 네 번째 동시성 방식(Redis Lua)과 선점 만료를 구현하고, Outbox와 Kafka로 이벤트를 전달하며, 가짜 결제 서버(mock PG)와 결제 흐름을 완성합니다.
- **하위 단계:** M3-1 Redis Lua 선점과 TTL 만료 → M3-2 Outbox와 Kafka → M3-3 결제(mock PG). 하위 단계마다 "스터디 → 각자 구현 → 회고" 사이클을 진행합니다.
- **선행 조건:** M2 완료, 공용 이벤트 봉투와 스키마 초안

## M3-1 Redis Lua 선점과 TTL 만료

- **미리 공부할 기술:** Redis Lua 스크립트와 원자성, 키 만료, 보상 처리, 조건부 UPDATE
- **관련 기능:** RSV-04, RSV-06

### 1. Lua 선점 전략

- **목표 동작:** 설정을 Lua로 바꾸면 좌석 확인과 선점이 Redis 스크립트 하나로 원자적으로 실행되고, 시나리오 1에서 초과 판매가 0건입니다.
- **관련 기능:** RSV-06, RSV-01
- **확인 방법:** M2의 동시성 테스트와 공용 불변식 검사기
- **결정 의존:** 없음

### 2. Redis와 DB 불일치 보상

- **목표 동작:** Redis 선점은 성공했지만 DB 반영이 실패하면 Redis의 선점이 되돌려져, 그 좌석을 다시 선점할 수 있습니다.
- **관련 기능:** RSV-01
- **확인 방법:** DB 반영을 일부러 실패시킨 뒤 Redis 상태와 재선점 가능 여부를 확인하는 통합 테스트
- **결정 의존:** 없음

### 3. 선점 만료 스위퍼

- **목표 동작:** 결제 마감 시각이 지난 `PENDING` 예약은 주기 스위퍼가 조건부 UPDATE로 `EXPIRED`로 바꾸고 좌석을 `AVAILABLE`로 돌려줍니다. 같은 예약을 두 번 만료시키지 않고, 서버가 여러 대여도 스위퍼는 한 번만 실행됩니다.
- **관련 기능:** RSV-04. Redis 키 만료는 보조 수단으로만 활용합니다.
- **확인 방법:** 시각에 따른 만료를 확인하는 테스트, 스위퍼 두 개를 동시에 실행해도 한 번만 처리되는지 확인하는 테스트(M1-2 작업 8의 ShedLock과 같은 방식)
- **결정 의존:** 노션 정책서의 "선점 유지 시간"

### M3-1 완료 조건

Lua 방식도 시나리오 1에서 초과 판매가 0건이고, 만료된 `PENDING` 예약의 좌석이 회수됩니다.

- **ADR 후보:** TTL 만료 설계(DB 스위퍼 기본, Redis 만료 보조)

## M3-2 Outbox와 Kafka

- **미리 공부할 기술:** Transactional Outbox, Kafka 생산자·소비자와 오프셋, 멱등 소비, DLT
- **관련 기능:** MSG-01~04, AUTH-05·ORG-01(이벤트 발행)

### 1. Outbox 기록

- **목표 동작:** 예약 상태가 바뀌면 같은 트랜잭션 안에서 Outbox 테이블에 이벤트가 기록되고, 트랜잭션이 롤백되면 이벤트도 남지 않습니다.
- **왜 하는가:** DB에 저장한 뒤 Kafka로 바로 보내면, 저장은 됐는데 발행 직전에 서버가 죽어 이벤트가 사라지거나, 반대로 발행한 뒤 DB가 롤백되어 없는 사실이 퍼질 수 있습니다(이중 쓰기 문제). 이벤트를 같은 트랜잭션으로 DB 테이블에 먼저 기록하면 상태 변경과 이벤트가 항상 함께 성공하거나 함께 실패합니다.
- **관련 기능:** MSG-01
- **확인 방법:** 커밋과 롤백 각각의 Outbox 행을 확인하는 통합 테스트
- **결정 의존:** 노션 정책서의 "이벤트 형식", 공용 이벤트 스키마

### 2. Outbox 폴러와 Kafka 발행

- **목표 동작:** 폴러가 아직 발행하지 않은 Outbox 이벤트를 공용 스키마 형식으로 Kafka에 발행하고, 발행이 끝난 이벤트는 다시 발행되지 않게 처리합니다. 처리 방식(표시, 삭제 등)은 각자 정합니다.
- **관련 기능:** MSG-01
- **확인 방법:** Testcontainers(Kafka)로 발행된 메시지의 형식과 순서를 확인합니다.
- **결정 의존:** 없음

### 3. 멱등 컨슈머

- **목표 동작:** 같은 이벤트 ID의 메시지를 여러 번 받아도 처리 결과는 한 번만 반영됩니다.
- **왜 하는가:** Kafka는 메시지 유실을 막기 위해 같은 메시지를 두 번 이상 전달할 수 있습니다(최소 한 번 전달). 그래서 받는 쪽이 이미 처리한 이벤트인지 확인해 중복을 걸러야 합니다. 작업 2의 폴러도 발행 직후 장애가 나면 같은 이벤트를 다시 발행할 수 있습니다.
- **관련 기능:** MSG-02
- **확인 방법:** 같은 메시지를 N번 보낸 뒤 처리 결과가 1건인지 확인하는 통합 테스트
- **결정 의존:** 없음

### 4. 실패 메시지 격리

- **목표 동작:** 정해진 횟수만큼 재시도해도 실패한 메시지는 DLT로 보내지고, 뒤따르는 정상 메시지는 계속 처리됩니다.
- **관련 기능:** MSG-03
- **확인 방법:** 처리에 실패하는 메시지와 정상 메시지를 섞어 보낸 뒤 DLT와 처리 결과를 확인하는 통합 테스트
- **결정 의존:** 노션 정책서의 "재시도 횟수"

### 5. 예약 확정 알림 컨슈머

- **목표 동작:** 예약 확정 이벤트를 받으면 모놀리스 내부의 알림 컨슈머가 로그나 이메일 mock으로 알림을 보냅니다.
- **관련 기능:** MSG-04. 예약 확정 이벤트를 실제로 만드는 것은 M3-3 작업 7이므로, 이 단계에서는 테스트에서 이벤트를 직접 발행해 확인합니다.
- **확인 방법:** 이벤트를 발행한 뒤 알림 mock이 호출되는지 확인하는 통합 테스트
- **결정 의존:** 없음

### 6. 회원 탈퇴와 행사 변경 이벤트 발행

- **목표 동작:** 회원이 탈퇴하거나 주최자가 행사를 바꾸면 해당 이벤트가 Outbox를 거쳐 Kafka로 발행됩니다.
- **관련 기능:** AUTH-05, ORG-01
- **확인 방법:** 각 동작 후 발행된 메시지를 확인하는 통합 테스트
- **결정 의존:** 공용 이벤트 스키마에 두 이벤트가 정의되어 있어야 합니다.

### M3-2 완료 조건

같은 이벤트가 N번 전달되어도 처리 결과가 1건으로 수렴합니다.

## M3-3 결제(mock PG)

- **미리 공부할 기술:** 결제 상태 머신, 웹훅 서명 검증, Resilience4j 서킷브레이커와 재시도, 멱등 키, 조건부 상태 전이, Saga(작업 7~8의 "만료 후 승인되면 환불"이 보상 처리의 예입니다)
- **관련 기능:** PG-01~03, PAY-01~05, RSV-03(환불 연동), RSV-05

### 1. mock PG 결제 승인

- **목표 동작:** `mock-pg` 서버에 결제를 요청하면 결제 키를 돌려주고, 일정 시간 뒤 결과 웹훅을 보냅니다. 같은 멱등 키(예: 주문 ID)로 다시 온 요청은 새 결제를 만들지 않고 처음 결과를 돌려줍니다.
- **관련 기능:** PG-01
- **확인 방법:** `mock-pg` 모듈의 API 테스트와 웹훅 발송 확인, 같은 멱등 키로 두 번 요청했을 때 결제가 한 건인지 확인
- **결정 의존:** 없음

### 2. mock PG 환불

- **목표 동작:** `mock-pg` 서버에 결제 키로 환불을 요청하면 환불이 처리됩니다.
- **관련 기능:** PG-02
- **확인 방법:** `mock-pg` 모듈의 API 테스트
- **결정 의존:** 없음

### 3. mock PG 장애 모드

- **목표 동작:** 설정 API로 응답 지연, 실패 비율, 웹훅 중복 발송, 웹훅 누락을 켜고 끌 수 있습니다.
- **관련 기능:** PG-03
- **확인 방법:** 모드별로 응답과 웹훅이 설정대로 바뀌는지 확인하는 테스트
- **결정 의존:** 없음

### 4. 결제 요청

- **목표 동작:** 구매자가 `PENDING` 예약의 결제를 요청하면 결제가 `READY`로 만들어지고 mock PG의 결제 키를 받으며, 결제 마감 시각이 지났으면 거절됩니다. mock PG에는 예약마다 하나인 멱등 키를 함께 보냅니다.
- **관련 기능:** PAY-01
- **확인 방법:** 정상 요청과 마감 후 요청의 거절을 확인하는 통합 테스트
- **결정 의존:** 노션 정책서의 "결제와 만료 경합"

### 5. 결제 결과 웹훅 수신

- **목표 동작:** 서명이 올바른 웹훅만 받아들여 결제를 `APPROVED`나 `FAILED`로 바꾸고, 같은 웹훅이 여러 번 와도 한 번만 반영하며, 승인되면 결제 승인 이벤트를 Outbox에 기록합니다.
- **왜 하는가:** 웹훅 주소는 외부에 열려 있으므로 누구나 "결제 승인" 요청을 위조해 보낼 수 있습니다. mock PG와 미리 나눠 가진 비밀 키로 만든 서명을 검사해야 진짜 요청만 받을 수 있습니다.
- **관련 기능:** PAY-02
- **확인 방법:** 잘못된 서명의 거절, 중복 웹훅 N건의 결과 1건 수렴, Outbox 기록을 확인하는 통합 테스트
- **결정 의존:** 노션 정책서의 "웹훅 검증"

### 6. 결제 조회

- **목표 동작:** 구매자가 자기 결제의 상태와 금액을 조회할 수 있습니다.
- **관련 기능:** PAY-03
- **확인 방법:** API 테스트
- **결정 의존:** 없음

### 7. 예약 확정과 만료 경합 처리

- **목표 동작:** 결제 승인 이벤트를 받으면 `PENDING` 예약은 `CONFIRMED`, 좌석은 `SOLD`가 됩니다. 그 사이 예약이 이미 `EXPIRED`가 되었으면 조건부 상태 전이로 확정하지 않고 환불을 요청합니다.
- **관련 기능:** RSV-05
- **확인 방법:** 정상 확정과, 만료가 먼저 반영된 경우의 환불 요청을 각각 확인하는 통합 테스트
- **결정 의존:** 노션 정책서의 "결제와 만료 경합"

### 8. 환불과 확정 예약 취소

- **목표 동작:** 구매자가 `CONFIRMED` 예약을 취소하거나 작업 7에서 환불이 필요해지면 mock PG에 환불을 요청하고, 결제는 `REFUNDED`, 예약은 `CANCELED`, 좌석은 `AVAILABLE`이 됩니다.
- **관련 기능:** PAY-04, RSV-03
- **확인 방법:** 두 경로 각각의 최종 상태를 확인하는 통합 테스트
- **결정 의존:** 노션 정책서의 "취소·환불"

### 9. PG 장애 대응

- **목표 동작:** mock PG 호출에 타임아웃, 재시도, 서킷브레이커가 적용되어, 서킷이 열리면 결제 요청이 바로 실패로 돌아오고 해당 예약은 `PENDING`으로 남았다가 정상 만료됩니다. 재시도해도 결제는 한 번만 만들어집니다(작업 1·4의 멱등 키).
- **왜 하는가:** 응답하지 않는 PG를 계속 기다리면 요청 스레드가 쌓여 결제와 무관한 기능까지 느려집니다. 서킷브레이커는 실패가 일정 비율을 넘으면 한동안 호출 자체를 막아 장애가 번지는 것을 막습니다. 다만 첫 요청이 실제로는 성공했는데 응답만 늦은 경우가 있으므로, 재시도에는 멱등 키가 함께 필요합니다.
- **관련 기능:** PAY-05
- **확인 방법:** mock PG 장애 모드를 켠 뒤 서킷 열림, 즉시 실패, 이후 만료를 확인하는 통합 테스트. 응답 지연 모드에서 재시도가 일어난 뒤에도 결제가 한 건인지 확인합니다.
- **결정 의존:** 없음

### M3-3 완료 조건

중복 웹훅 N건이 결과 1건으로 수렴하고, mock PG 장애 시 예약이 `PENDING`에서 정상 만료됩니다. 여기까지가 M3의 완료 조건입니다.

- **ADR 후보:** 결제 성공과 만료의 경합 처리 방식
