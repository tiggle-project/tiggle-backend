# 작업 단위 진행 규칙

## 작업 단위

- 작업 단위는 Issue handoff 5절에 적힌 단위 하나다. 단위를 나누는 기준과 계획 승인 절차는 [handoff_convention.md](./handoff_convention.md)의 "작업 단위 설계", "작업 단위 계획 공유와 승인"을 따른다.
- 한 채팅에서는 하나의 작업 단위만 진행한다. 구현, 검증, handoff 갱신, 보고를 마치면 멈추고, 사용자가 diff를 리뷰하고 직접 커밋한 뒤 다음 단위로 넘어간다.
- 현재 단위를 보완하거나 수정하는 후속 요청은 같은 단위에 포함한다. 계획에 없는 별도 목표는 새 작업으로 보고, 필요하면 handoff에 단위를 추가하는 계획 갱신부터 한다.
- 단위 진행 중 계획 밖 변경이 필요해지면 [handoff_convention.md](./handoff_convention.md)의 "작업 단위 계획 공유와 승인"에 따라 구현을 멈추고 계획 갱신안으로 확인받는다.
- 작업 시작 시 `git status --short`로 기존 사용자 변경과 이번 단위의 변경을 구분하고, 기존 변경은 보존한다.

## 테스트와 검증

실행할 테스트 범위와 미실행 보고는 [testing_convention.md](../project_code_convention/testing_convention.md)의 "Which Tests to Run"을 따르고, 매 작업 단위에서 `git diff --check`를 함께 실행한다.

## 코드 배치와 포맷

- import 순서는 사용자 IDE 포맷터 결과를 따른다. 프로젝트마다 정해 두는 것이 좋다(예: 한 블록, ASCII 정렬, 그룹 사이 빈 줄 없음). 직접 수정하지 않는 파일의 import는 재정렬하지 않는다.
- 클래스 안에서 private 메서드는 public 메서드 아래에 둔다. 공개 계약이 먼저 읽히게 하기 위해서다.
- 사용자 IDE 포맷팅으로 생긴 변경(import 순서, 들여쓰기, 줄바꿈)은 되돌리지 않고 보고와 handoff에 기록한다. 단, IDE 재배치로 private 메서드가 public 위로 올라갔다면 위 규칙대로 되돌린다.

## 작업 후 답변 스타일

이 절은 독자(사용자)가 트랜잭션, 잠금, 전파 속성 같은 기술 개념은 알고, 모르는 개념은 외부 자료로 따로 확인하며, 어려워하는 것은 도메인 로직이라고 가정한다. 독자가 다르면 이 절의 전제를 조정한다. 그래서 답변은 개념 설명보다 "왜 필요한가"와 "어디에 연결되는가"를 먼저 쓴다. 일반 개념 설명은 질문을 받기 전에는 줄인다.

- 형식: 표 대신 목록으로, 실무적이고 일관된 존댓말로 짧게 쓴다.
- 파일 링크: 파일이나 메서드를 언급할 때마다 워크스페이스 기준 상대 경로 Markdown 링크를 달고, 위치가 중요하면 `#L줄번호`를 붙인다.
- 리뷰 포인트: 사용자는 매 채팅의 diff를 직접 확인한 뒤 다음으로 넘어간다. 정책이나 확정된 결정이 반영된 코드 줄은 답변 앞쪽에 "리뷰할 곳"으로 모으고 ⚑를 붙인다. 정책과 다르게 구현한 부분이 있으면 먼저 밝힌다.
- 파일 나열 순서: 변경 파일은 사용자가 코드 리뷰를 쉽게 하도록 읽는 순서대로 나열한다. 계약과 타입(인터페이스, 코드 enum)을 먼저, 그 계약을 쓰는 구현을 다음에, 테스트를 마지막에 둔다. 다른 파일이 의존하는 파일이 앞에 오게 하고, 흐름도와 변경 파일별 설명, 커밋 제안의 `git add` 대상도 같은 순서를 따른다.
- 변경 파일별 설명: 파일마다 아래를 빠짐없이 쓴다. handoff에 기록하는 작업 단위 내용도 같은 항목을 따라 채팅 보고와 어긋나지 않게 한다.
  - 역할과 기능: 무엇을 하고 무엇을 하지 않는지, 호출하는 쪽이 지켜야 할 전제
  - 쓰이는 곳: 지금 호출하는 곳과 앞으로 호출할 곳. 호출자가 아직 없으면 "미연결"이라고 쓰고, 예정된 호출을 이미 실행되는 것처럼 쓰지 않는다.
  - 없으면 안 되는 이유: 변경이 없으면 무엇이 깨지는지 구체적인 예시 하나
  - 전/후 비교: 작업 전과 후의 코드 상태
- 락, 쿼리, 트랜잭션 경계: 새로 추가하거나 설명하는 것마다 "없으면 어떤 사용자 시나리오에서 어떤 데이터가 깨지는가"를 정책 → 시나리오 → 코드 순서로 한 줄 적는다.
- 흐름도: 여러 메서드에 걸친 기능은 단계별 흐름도 하나에 각 단계의 링크와 구현, 미연결 상태를 표시한다.
- 결정 요청: 사용자가 정할 일은 선택지, 추천, 추천 이유를 함께 내고 임의로 확정하지 않는다.
- 커밋 제안: 작업 단위가 끝나면 히스토리의 prefix(`feat:`, `fix:`, `chore:` 등)로 커밋 메시지를 제안한다. 목적이 다른 변경이 섞여 있으면 커밋 분리안과 커밋별 `git add` 대상을 함께 낸다. 커밋은 사용자가 직접 하며, 요청이 없으면 에이전트가 커밋하지 않는다.
- 주석 작성 규칙은 [comment-style.md](./comment-style.md)를 따른다.
