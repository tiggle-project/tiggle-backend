# 핸드오프 문서 컨벤션

## 목적과 원칙

세션이 바뀌어도 현재 작업 상태, 확정된 기술 계약, 구체적인 작업 단위와 다음 작업의 범위를 잃지 않도록 핸드오프를 일관된 구조로 유지한다. 이 문서는 핸드오프 작성과 갱신 방법, 작업 단위를 설계하는 기준을 정한다. 한 채팅의 진행 방식, 테스트 범위, 답변 스타일은 [work_scope_convention.md](./work_scope_convention.md)를 따른다.

- 규칙 원문이나 계획 본문은 다른 문서로 복사하지 않고 링크한다. 같은 계획과 규칙을 handoff와 future plan에 장문으로 중복 기록하지 않는다.
- 실제로 구현, 실행하지 않은 것을 완료나 통과로 기록하지 않는다. 존재하지 않는 경로나 폐기된 구조를 현재 규칙처럼 쓰지 않는다.
- 사용자가 명시하지 않은 문서 구조를 임의로 제거하거나 복구하지 않는다.

## 문서 역할

- `docs/handoff/issue-{number}-handoff.md`: 특정 GitHub Issue의 범위, 계약, 작업 단위 계획, 진행 상태, 검증 결과, 남은 위험
- `docs/handoff/plan/future-plan.md`: 단계(Gate) 순서, 미구현 범위, 완료 기준, 프로젝트 완성 기준
- `docs/handoff/legacy/`: 사용자가 보관하는 종료된 문서. 참고 자료일 뿐 현재 상태의 기준이 아니며, 삭제, 이동, 정리하지 않는다.

문서가 서로 다르면 `AGENTS.md` → `work_scope_convention.md` → `docs/project-overview.md`(제품 맥락 문서) → 현재 코드, 테스트, 설정 → Issue handoff → future plan → `legacy/` 순서로 판단한다.

## Issue handoff 파일

- 파일명은 `docs/handoff/issue-{number}-handoff.md`이고 `{number}`에는 Issue 번호만 넣는다. 예: `issue-28-handoff.md`
- 같은 Issue의 후속 세션은 기존 파일을 갱신하고 `-2` 같은 새 파일을 만들지 않는다.
- Issue가 끝나도 삭제하거나 `legacy/`로 옮기지 않는다. 사용자가 요청한 경우에만 옮기고, 옮길 때는 문서 안의 상대 링크와 다른 문서에서 이 문서를 가리키는 링크를 함께 고친다.
- 핸드오프를 처음 만들 때 5절에 아래 "작업 단위 설계" 기준으로 나눈 구체적인 작업 단위 목록까지 작성한다. 정책 결정이 남아 단위를 확정할 수 없으면 확정 가능한 단위는 모두 쓰고, 나머지는 결정 대기 항목과 그 결정에 따라 생길 단위 후보로 적는다.

## Issue handoff 구조

0. **참조 문서**: AGENTS.md의 참조 문서를 핸드오프 위치 기준 상대 링크로 한 번씩 나열하고, 역할과 이 이슈에서의 적용 시점을 한 줄로 적는다. 갱신 때 최신 AGENTS.md와 대조하고, 없는 경로는 누락 사실만 기록한다. 실제로 읽은 문서와 적용한 규칙은 목록과 구분해 적는다. AGENTS.md가 참조하지 않는 추가 기준 문서는 따로 구분한다.
1. **이슈와 브랜치**: Issue 번호, 제목, 브랜치, HEAD, 작업 트리 상태. GitHub 상태는 실제 확인과 로컬 판단을 구분한다.
2. **목표와 범위**, **제외 범위와 선행 조건**
3. **프로젝트 맥락**: 제품 목적과 이 이슈가 끼워지는 구조를 짧게. 코드에 없는 기능은 "계획"으로만 쓴다.
4. **핵심 기술 계약**: 입력, 출력, 오류 경계, 비밀값, 제외 범위. 현재 실행 계약과 향후 산출물 계약을 구분한다.
5. **작업 단위와 현재 상태**: 계획 승인 상태(승인 전, 승인 날짜, 갱신 이력)와 작업 단위 목록. 단위마다 아래 "단위마다 적을 것"과 상태(`pending`, `in progress`, `done`), 나눈 근거(해당하는 분할 조건)를 적는다. 완료 단위는 아래 "크기 관리"대로 압축하고, 설계 결정과 구현 결과를 함께 적는다.
6. **검증 상태**: 실행한 명령 그대로, 통과, 실패, 미실행 구분. 실패는 코드 문제와 환경 문제를 구분한다. 실제 검증 환경(예: Docker로 띄운 DB, 캐시)을 인메모리 대체물로 잘못 기록하지 않는다.
7. **남은 위험과 다음 작업**: 다음 작업은 하나의 기능이나 단위로 좁히고, future plan에 있는 작업은 링크로 참조한다.
8. **바로 다음 채팅 작업 (pending)**: 계획 승인 전이면 승인 대기 항목, 승인 후면 다음 단위 하나의 번호와 목적, 대상 파일, 수정하지 않을 범위, 검증 명령. 완료 상태와 섞이지 않게 `pending`으로 표시하고, 그 이후 순서는 5절 단위 목록이나 future plan으로 참조한다.

## 작업 단위 설계

작업 단위는 파일 수가 아니라 "독립적으로 검증되는 동작 하나"로 자른다. 파일 수로 자르면 동작이 깨진 중간 커밋이 생기고(예: 입력을 받는 parser만 등록돼 처리하는 쪽이 없어 결과에서 항목이 조용히 빠지는 상태), 계획에 있던 내용을 단위마다 다시 승인하는 왕복이 생기기 때문이다.

### 단위의 정의

단위 하나는 아래를 모두 만족한다.

- 목표 동작을 "X하면 Y가 된다"는 한 문장으로 쓸 수 있다. 문장에 "그리고"가 들어가면 두 단위인지 다시 본다.
- 그 동작을 확인하는 테스트가 있다. 버그와 기능은 수정 전 실패, 수정 후 통과하는 테스트를, 동작을 바꾸지 않는 리팩터링은 기존 golden과 회귀 테스트 불변을 근거로 한다.
- 단위가 끝난 커밋은 정상 상태다. 테스트가 통과하고, 사용자가 부분 구현된 기능을 만날 수 없다.

### 반드시 나누는 경우

하나라도 해당하면 다른 단위로 나눈다.

1. 변경 성격이 다르다: 동작 변경, 동작을 바꾸지 않는 리팩터링, 문서만 바꾸는 변경은 섞지 않는다. 섞으면 golden이 바뀐 이유를 구분할 수 없다.
2. 결정 의존이 다르다: 사용자 정책 결정이 필요한 변경과 필요 없는 변경은 나눈다. 결정 대기가 다른 변경을 막지 않게 한다.
3. 도메인이 다르다: 인증, 프로젝트, 결제처럼 서로 다른 도메인(패키지)의 변경은 나눈다.
4. 실행 경로가 다르다: 같은 도메인이라도 로컬 실행과 클라우드 배포, REST와 WebSocket처럼 회귀 범위가 다른 경로는 나눈다.
5. 영속 구조가 바뀐다: 엔티티 컬럼, 테이블, 인덱스 변경은 그것을 쓰는 첫 동작과 함께 하되 다른 변경과 섞지 않는다.

### 나누면 안 되는 경우

- 새 코드와 그 코드의 첫 호출자: 에러 코드와 그 코드를 던지는 검사, 인터페이스 메서드와 첫 구현처럼 단위 안에서 만든 코드는 단위 안에서 호출된다. 호출자 없는 코드만 담긴 커밋을 만들지 않는다.
- 동작과 그 동작의 테스트: 테스트를 다음 단위로 미루지 않는다.
- 변경 때문에 깨지는 기존 테스트의 수정: golden 갱신, fixture 보강은 원인이 된 변경과 같은 단위에 넣는다.

### 순서

- 기능에 필요한 리팩터링이 있으면 리팩터링 단위를 먼저 둔다.
- 입력을 여는 변경(parser 등록, API 노출, enum 허용 등 사용자가 새 경로로 들어오게 하는 변경)은 그 경로를 처리할 service, 출력 코드가 준비된 뒤 마지막에 둔다. 먼저 만든 처리 코드는 입구가 없어 호출되지 않으므로 안전하다.
- API, 에러 코드 계약 문서는 이슈 마지막 문서 단위로 모으는 것을 기본으로 한다. 동작 단위에 함께 넣어야 리뷰가 쉬우면 그렇게 적는다.
- 결정을 기다리는 단위는 결정 이후에 배치한다.

### 크기 신호

크기는 자르는 기준이 아니라 다시 보라는 신호다. 아래 중 하나에 해당하면 더 나눌 수 있는지 보고, 나누지 않으면 이유를 5절에 적는다.

- 비문서 파일(구현, 설정) 6개 이상
- 테스트를 제외한 diff 300줄 이상
- 단위 작업 보고의 흐름도가 7단계를 넘는다

### 단위마다 적을 것

- 목표 동작(한 문장)
- 변경 파일 목록(비문서와 테스트 구분)
- 테스트: 추가, 수정 대상과 수정 전 실패 여부
- 검증 명령
- 결정 의존 여부
- 끝난 상태: 무엇이 동작하고 무엇이 아직 막혀 있는지

## 크기 관리

핸드오프는 새 세션이 가장 먼저 읽는 문서라 길어질수록 매번 컨텍스트를 소모한다. 상세 이력은 git과 코드에 있으므로 핸드오프에는 다음 세션에 필요한 것만 남긴다.

- 완료된 작업 단위는 커밋 해시, 변경 파일, 핵심 결정과 그 이유, 한계로 압축한다. 파일별 역할, 쓰이는 곳, 전/후 설명은 진행 중인 단위나 사용자가 커밋하기 전 단위에만 둔다.
- 검증 상태는 단위별 최신 결과만 남기고, 같은 명령의 과거 실행 기록이나 해소된 확인 기록은 지운다.
- 해소된 위험, 지나간 중간 상태, 이미 반영된 "다음 작업"은 지운다. 결정이 바뀌었으면 최종 결정과 바뀐 이유만 남긴다.
- 반복 적용할 규칙은 harness 문서로 옮기고 핸드오프에는 링크만 남긴다.

## Future plan 구조

- 현재 기준(구현과 미구현 구분), 실행 순서, 기술 범위(입력, 산출물, 실행 위치, 인증, 비밀값 경계), 코드, 테스트, 명령으로 확인 가능한 완료 기준을 기록한다.
- 다음 이슈는 목적과 범위만 쓰고 Issue Template 본문은 저장하지 않는다. 이슈별 실행 상세는 해당 handoff에 두고 링크한다.

## 갱신 절차

1. `git status --short`, 현재 브랜치, 최근 커밋을 확인한다. 사용자는 작업 단위마다 직접 커밋하므로, 기록된 HEAD 이후 새 커밋이 있으면 HEAD와 작업 트리 기록을 갱신한다.
2. 최신 요청과 해당 Issue handoff를 읽고, 없으면 작업 단위 목록까지 포함해 만든다.
3. 변경 대상 코드와 인접 테스트를 확인한다.
4. 승인된 작업 단위 계획이 없으면 아래 "작업 단위 계획 공유와 승인"을 따른다. 사용자가 맥락 파악이나 설명만 요청했거나 수정을 금지했다면 계획 공유와 상태 요약에서 멈춘다.
5. 승인된 계획이 있으면 5절의 다음 `pending` 단위 하나를 구현하고 work_scope_convention의 검증을 실행한다.
6. 완료, 미완료, 계획을 분리해 handoff를 갱신하고 "크기 관리"를 적용한다. 단위 상태와 8절 pending을 다음 단위로 옮긴다.

## 작업 단위 계획 공유와 승인

이슈나 기능을 착수할 때 코드보다 작업 단위 계획을 먼저 공유하고 승인받는다. 승인은 계획 전체에 한 번 받고, 단위마다 설계를 다시 승인받지 않는다.

- 공유 내용: 목표, 현재 동작, 변경 후 흐름, 선택 이유와 대안, 사용하지 않을 범위, 가정, 위험, 사용자 결정이 필요한 항목(선택지, 추천, 이유), 그리고 "작업 단위 설계" 기준으로 나눈 단위 목록(단위마다 "단위마다 적을 것"과 분할 근거)
- shell script, CI workflow, 외부 연동, rollback, migration처럼 운영 위험이 있는 요소는 일반 개발자가 이해할 수 있는 예시로 설명한다.
- 사용자가 승인하기 전에는 파일 생성, 수정, 삭제, 이동이나 외부 시스템 변경을 하지 않고 읽기 전용 조사와 안전한 검증만 한다. 핸드오프 문서 작성과 갱신은 예외다. "진행해줘" 같은 포괄적인 요청이나 Issue 본문만으로 계획이 승인된 것으로 보지 않는다. 승인 대상은 handoff 5절에 적힌 단위 목록이다.
- 결정 대기 항목이 있는 단위는 결정 전까지 승인되지 않은 것으로 보고, 결정이 필요 없는 단위부터 진행할 수 있다.
- 승인 후 계획에 없는 파일, 추상화, 정리, 주석 삭제, 도구 도입, 정책 판단, 동작 변경이 필요해지면 구현을 멈추고 계획 갱신안을 내서 다시 승인받는다. 단위가 예상보다 커지면 "단위의 정의"를 만족하는 지점에서 끊고 나머지를 다음 단위로 추가한다. 갱신 내용과 이유는 5절 갱신 이력에 남긴다.
- handoff에는 `설계 공유`, `사용자 확인`, `구현 결정`, `구현 결과`를 구분해 기록한다.
- 작업 중 사용자가 정한 코드 스타일이나 작업 방식은 `사용자 확인`에 기록한다. 반복 적용할 규칙이면 같은 작업 단위 안에서 관련 harness 문서에 반영하고 handoff에는 링크만 남긴다.
